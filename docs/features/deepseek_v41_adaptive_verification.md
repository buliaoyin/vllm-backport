# DeepSeek-V4.1 混合推理：DSpark 动态草稿预算

在已有 CPU/GPU 混合推理命令中，替换以下参数即可启用：

```bash
--speculative-config '{"method":"dspark","num_speculative_tokens":7,"enable_adaptive_verification":true}'
```

`num_speculative_tokens` 是最大草稿预算。设置为 7 时，调度器在 **1～7**
之间选择，包含 2、4、6；设置为 5 时选择 **1～5**。其他参数、流水线分层和 KV
预算沿用原配置。该选项默认关闭。

## 选择方式

- 单请求纯 decode 结合模型置信度头和实际采纳前缀估计下一轮收益，并用实际
  采纳结果校准预测。不会按“代码”“写作”等标签选档；缺少置信度头时退回实测策略。
- 单请求使用稳定的相对成本先验，避免把路由变化与计时波动误当成草稿长度的
  成本差异；新请求不沿用上一题的单请求计时估计。
- 并发或混入 prefill 时，先测两个预算的完整步骤耗时，再实测预期收益较高的
  候选并定期探测，选择预计“实际输出 token 数／耗时”较高的预算。
  初始测量和探测使用正常请求，不额外生成用户可见内容。
  按同批请求数、上下文长度和是否混有 prefill 分别保存实测成本。
- 只更新实际观察到的采纳前缀与首个拒绝位置。未验证的位置不会算作拒绝。
- 短预算下，如果查询块还有已算出的下一位置，用最后一个草稿预测该位置的
  采纳概率，帮助判断是否升档；不为此额外生成 token 或运行词表输出头。

置信度随对应验证步骤的输出异步返回，复用已有复制与同步事件。反馈存在流水线
延迟。首次有效反馈即可参与选档；随后预算切换设有保持期和收益门槛，减少
小幅波动引起的反复切换。

同一批请求的下一轮起草使用相同预算。已经生成的草稿按原长度验证；所有 PP
阶段都接收调度器给出的准确 token 边界，保留 CED、草稿回退和异步流水线的同步规则。

## 范围与限制

这里复用官方的 `enable_adaptive_verification` 开关；DeepSeek-V4.1 混合模式
使用调度器上的置信度校准与实测策略，其他模型保留原有置信度策略与支持限制。
混合模式要求 V2 Model Runner、异步调度和 CUDA Graph，不能同时指定
`num_speculative_tokens_per_batch_size`，也不支持 LoRA。

**实际草稿生成数量会随预算缩短，不再始终生成最大数量后裁剪验证。** 对应的
CUDA Graph 在启动时捕获。预算不超过 5 时保留训练时的 5 个查询位置，缩短输出头
和 Markov 生成循环；6、7 档分别使用 6、7 个查询位置。显式指定更短的
`dspark_num_query_tokens` 时仍受配置上限约束。
验证图按查询长度分别匹配，并保留最大预算的请求数网格，避免缩短预算后
因捕获尺寸稀疏而退回普通执行。
KV、显存工作区和专家缓存仍按最大预算规划，不随每轮选择缩小。

动态选择存在测量和探测成本。低采纳率任务可能受益，高采纳率任务也只有在多
采纳的 token 足以抵消验证成本时才适合升档。并发批次中的任务可能需要不同
预算，目前仍选择统一预算；长 prefill 造成的流水线阻塞也不会因此消失。
部署前应同时比较固定 3、固定 5、固定 7 和动态预算，计入完整输出阶段及 prefill
插入停顿。比较时核实实际起草数量和查询长度；原生固定配置应单独启动测量，
不能把动态服务内强制固定选档的结果直接当作原生部署性能。

运行日志中的 `Adaptive DSpark drafting` 给出当前批次请求数、下一轮起草预算、
是否混合 prefill，以及各预算累计完成的请求验证轮数。各草稿位置的官方
`Per-position acceptance rate` 不能直接当作本策略的条件采纳率。
