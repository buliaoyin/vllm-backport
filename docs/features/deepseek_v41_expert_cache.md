# DeepSeek V4.1 混合推理专家缓存

GPU 常驻热点专家，其余路由由 CPU 处理。缓存根据 verification-group
路由反馈和跨请求 EWMA 更新专家选择，已有 host packed/LRU 缓存、收益阈值和
替换预算。热点持久化默认保存驻留名单和学习状态，供同一模型重启时恢复，也可关闭。

## 配置

以下字段位于 `--additional-config` 的 `deepseek_v41_hybrid` 对象中：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `expert_profile` | 按模型指纹生成路径 | 读取、保存学习状态的 JSON 路径，支持 `~`；`false` 关闭持久化。 |
| `expert_profile_interval` | `16` | 两次保存尝试之间的请求组结束次数，正整数；默认路径也可设置，关闭持久化时不可设置。 |
| `overlap_decode` | `true` | 方案 A：先提交 draft，再完成 CPU 专家错误检查、采样计数及缓存维护。只接受布尔值。 |
| `r8_refill` | `true` | 从 CPU 原生 R8 bank 搬入并直接重排到 Marlin；使用较早的 decode 热点更新。只接受布尔值。 |
| `host_cache_gib` | `0` | 主存 Marlin LRU 预算，单位 GiB，范围 0–64；`0` 关闭，不影响 GPU 热点缓存。 |
| `adaptive_cache` | `false` | 按 decode 热度和 CPU 成本，在同一卡的缓存层之间动态调整容量。支持 `true` 或策略对象。 |

未指定 `expert_profile` 时，自动使用
`$VLLM_CACHE_ROOT/expert_profiles/deepseek_v41/<模型指纹>.json`。
沿用 vLLM 缓存目录约定：`VLLM_CACHE_ROOT` 优先，其次为 `$XDG_CACHE_HOME/vllm`，
均未设置时使用 `~/.cache/vllm`。同一模型重启复用文件，不同指纹使用不同文件。
启动日志中的 `Expert cache profile` 显示实际路径；显式配置的路径优先于默认路径。

例如三张 CMP 170HX：

```json
{
  "deepseek_v41_hybrid": {
    "pipeline_layers": [7, 8, 25],
    "cpu_threads": [24, 24],
    "engram_storage": "ram",
    "expert_profile": "/absolute/path/dsv41f-expert-profile.json"
  }
}
```

四卡的分层、CPU 线程和存储应使用对应硬件实测配置。RAM Engram 比 SSD 多占约
189 GiB 主存；内存不足时参见 [Engram SSD 存储](deepseek_v41_engram_ssd.md)。
`expert_profile` 和 `overlap_decode` 不要求重建 native 库；`r8_refill` 需要更新
`libdsv41_ik`，已有混合推理的构建要求见
[构建说明](../contributing/deepseek_v41_build.md)。

## CPU KV 卸载

可在混推启动命令中加入 `--kv-offloading-backend native --kv-offloading-size 32`，
启用 32 GiB 主存 KV 卸载，并保持 `--enable-prefix-caching`。
压缩器和 indexer 的循环暂存组不参与前缀命中、卸载或恢复；原始组编号和物理块映射
保持一致。CPU 前缀命中按可复用组的块边界对齐，并为 CED 留下至少一个完整的
sliding-window 重算窗口，重建请求独立的暂存状态。
稀疏保留时同时保存 CED 重算起点之前的 sliding-window KV，避免非整块长度的
前缀因存储、查询边界不一致而无法从 CPU 恢复。
native CPU 卸载在 PP 下为每个 worker 分配连续、按页对齐的独立区域，按区域批量
注册 pinned 内存，避免逐小块注册耗尽 CUDA 资源；各区域总量仍受卸载预算限制。
内置 `OffloadingConnector` 与无 connector 时共用紧凑的 GPU KV 池估算：
保留每个请求仍需的窗口和状态，再按整批在途 token、lookahead 和推测 token
预留共享临时空间，不为每个请求重复预留整个 batch 的窗口临时空间。
调度前回收已完成计算的旧窗口；回写源块被复用前，worker 等待对应搬运完成。
外部或自定义 connector 继续使用保守预留。比较 GPU KV 与专家容量时，可核对
`Reserving ... GiB KV per worker` 日志。

## 学习和恢复

1. 文件不存在时按默认选择启动。发送实际业务的代表性请求，让原有在线策略学习。
2. worker 的混合请求组全部结束后保存；第一份有效学习结果立即保存，之后按间隔保存。
   持续存在在途请求会推迟保存。停止进程不会额外强制保存尚未达到间隔的状态。
3. 同模型、同路径重启，出现 `Restored expert cache profile` 日志表示恢复成功。
   仍需重新加载、打包和上传专家，profile 不会省略模型加载或恢复 KV cache。
4. 恢复之前的驻留名单；容量缩小时优先保留历史更热的已选专家，增大时按历史补齐。
   启动容量和 GPU 放置仍由显存预算规划；开启 `adaptive_cache` 后在运行中调整层间容量。

启动规划完成逐层分配后，会按 8 个槽位补齐每张卡的剩余额度，优先扩充同一卡上
容量较小的已有缓存层。如果某张卡有至少 8 槽额度但没有分到缓存层，启动规划会
尝试将一层的部分缓存放到该卡，仅在全机总槽数增加时采用。每层缓存仍只放在一张卡，
少于专家总数。已有布局的扩充保留缓存设备，不超过扣除预留后的实测显存额度。
容量分配以实测显存约束为准；没有测出吞吐提升不构成缩容依据。启动校准见下节。

## 启动显存校准

混推启动先初始化 NCCL 和跨卡 CUDA 上下文，再读取每卡空闲显存。
`gpu_memory_utilization` 限制包括初始化占用在内的总预算，
模型、KV 和专家缓存只使用扣除启动占用后的剩余额度。
启动时已有的其他进程占用也从额度扣除，避免将其当作可用空间。
因此 `0.99` 不要求初始化后仍有 99% 显存空闲；后续 Graph 捕获和运行峰值
仍按对应的 1% CUDA 可用显存余量校准，不会跳过预算检查。
实际请求与预热可能有小幅差异，运行峰值观察器记录实测占用，供后续启动调整。

保留已有缓存时允许实际最低空闲显存比规划余量低最多 40%。例如 `0.99`
在 170HX 上的规划余量约 649 MiB，最低空闲至少约 389 MiB 时保持已有槽数。
Graph 校准和重启复用采用同一阈值；扩容仍按完整规划余量计算，不使用容忍区间
增加槽位。低于 60% 阈值时按完整规划余量重新收缩。运行峰值仍如实记录，
窗口内的偏差不会仅因峰值回写而触发下一次启动缩容。

MRV2 的完整 Graph 模式首次启动先分配较小的探测缓存，完成 Graph 捕获后全卡同步。
预热最大 prefill 分块、单请求、多请求和最大 decode 批次，并采样每张卡同时发生的
物理显存峰值。decode 预热先为各请求建立 CED 状态，按
`max_num_batched_tokens` 分批预填充，再合并全部请求执行完整并发的 decode；
单请求的预填充超过该上限时也分块执行，不缩小最终的 decode 并发数。
启用 prefix cache 时使用真实调度输入，覆盖 CED 回放、PP 发送缓冲、
采样和 DSpark，而普通 dummy 输入不会启用 CED。上下文长度受各 PP 的实际 KV
块数、共享前缀和 lookahead 约束。包括本卡 PP worker 和最后一级 worker 在远端卡上的占用，
避免把不同进程、不同时刻的分配器峰值相加；保留 Tensor 分配和初始模型 profile
中的独立多模态临时占用下限，采样器由本次调度预热测量。原 profile 中后来已常驻的
发送缓冲、工作区等不重复作为运行峰值扣除。

每卡缓存容量由捕获、预热完成后的空闲显存加回当前专家权重占用，再扣除
`(1 - gpu_memory_utilization)` 对应的余量和实测运行峰值增量计算，不再额外扣除
固定 0.5 GiB。`0.985` 在 170HX 上已预留约 0.95 GiB CUDA 可用显存。
物理占用已包含 KV、Graph、专家计算缓冲及 R8 暂存，不重复扣除。
按 8 个槽位对齐分配，扩充已有缓存层时保留其设备。
历史总槽数只用于对照，容量可以高于或低于原初筛估算。

重新分配前同步所有相关 GPU，释放旧 Graph 和输出引用，再释放缓存并重新捕获。
最终再次校验各卡的运行余量；不满足时重新收缩或调整放置。正常校准最多执行四轮。
末轮扩容失败时恢复本次启动中已通过的布局，再额外捕获、复核一次，
保留该布局已验证的运行峰值；恢复后仍不满足预算则启动失败。
已安全但达到轮数上限时保留已验证方案并打印 warning。
`Hybrid Graph calibration` 日志显示每卡捕获增量、空闲显存、运行峰值增量、
所需余量和槽位容量；`Hybrid final expert capacity` 显示最终槽数。

实测预算和工作区容量保存到
`$VLLM_CACHE_ROOT/startup_plan/dsv41_experts_<指纹>.json`，与热点名单独立。
指纹包含模型 checkpoint、配置、可见 GPU、CUDA 可用总显存、KV 布局、驱动、
Torch/CUDA、相关源码和 native 库。预算文件版本为 `2`，与热点名单文件的版本独立。
`route_tail_skip`、CPU 线程数、主存专家 LRU 预算、Engram 主存缓存大小、热点名单
路径及保存间隔不进入显存预算指纹；动态容量策略只保留池启停和 `min_experts`，
调整检查间隔、替换上限、学习及收益阈值可复用已测峰值。
native CPU KV 卸载开启后，仅调整主存容量也可复用；启停或切换 backend 仍区分。
单独调整 `gpu_memory_utilization` 时，按新比例和本次空闲显存重新计算槽数；
实际 KV 布局相同时可复用峰值。分层、并发、prefill/decode 上限、Graph 形状、
prefix cache、RAM/SSD 模式、`r8_refill` 和 `overlap_decode` 等影响显存的设置仍参与指纹。
指纹规则更新后，旧文件首次启动需要重新记录；后续上述策略参数变化可复用。
配置匹配时恢复工作区容量，按本次实际空闲显存调整槽数，完成正常 Graph 捕获。
布局与已验证布局一致时保留完整峰值并做 decode 快速校验；布局变化时重测完整上下文。
空间不足或记录失效时重新校准。配置指纹相同的已验证峰值始终保留，
缩容和重测不会将其降低。

首次或变化后的布局分别记录 prefill、decode 的物理峰值，避免将旧布局的暂存成本
当成新布局的精确测量。最后一级 worker 在活跃请求组期间通过 NVML 每 10 ms 采样
各卡实际空闲显存；新峰值超过已验证记录时，在请求组结束后原子更新预算文件。
此采样不额外同步 CUDA，只提高下一次启动的预留，不在请求中改变缓存容量或 Graph。
小请求不会降低大请求已测得的峰值；采样失败记录 warning，继续使用已验证预算。
启动中的串行预热仍可能低估实际排队峰值，因此首次配置应运行代表性大请求和并发，
重启后核对实际预留。峰值回写只影响后续启动，不立即修正当前服务的缓存容量。

`Hybrid cache startup finished` 显示捕获次数、耗时和复用状态，
`Updated expert budget from serving peaks` 表示实际请求提高了下次启动的预留。
删除预算文件可重新完整测量。预算复用不省略模型和 Engram 权重加载。
峰值验证仍需代表性大请求和并发；单张空闲显存截图
不能代替运行峰值。比较 `nvidia-smi` 时应直接读取 `memory.free`，不能把
`memory.total - memory.used` 当成空闲显存，后者未扣除 `memory.reserved`。

## 持久化边界

文件版本为 `1`，大小最多 1 MiB。仅保存各层 `selected` 专家 ID、`history` 调用频率、
`requests` 和 EWMA `mass`，不保存输入、输出文本、权重、GPU tensors 或 pending counters。
没有活跃 GPU cache 的层保留之前的历史记录；这些记录不表示当前驻留，也不会继续学习。

checkpoint fingerprint 包含模型路径/ID、revision、HF commit、配置，以及本地 safetensors
文件名、大小、mtime 和 index 内容摘要。它没有完整哈希数百 GB 权重；保留所有元数据却
手工替换权重内容不在这个快速检查的保证范围内。

文件缺失时重新学习；身份、版本、层号、专家 ID、频率或大小校验失败时记录 warning 并
忽略整份文件。保存使用同目录临时文件和 `os.replace`，失败不打断生成。各独立部署使用
独立路径；多个写入者共享路径时最后一次原子写入生效，不合并学习状态。

移除 `expert_profile` 即可使用默认路径；设为 `false` 并移除 `expert_profile_interval`
即可关闭持久化，恢复每次启动重新学习的行为。
GPU/CPU 既有数值舍入可能因缓存放置变化而改变生成内容和 DSpark 接受率，需要做模型评测。

## 按层自适应容量

在既有 `deepseek_v41_hybrid` 配置内增加 `"adaptive_cache": true` 即可开启，
不需要 DSpark，也不改变 PP 分层。默认关闭时，各层容量固定，层内热点专家仍可替换。

开启后，同一卡、同一 PP worker 的缓存层共享固定地址的 Marlin 槽池。
每张卡的总槽数和层的缓存设备保持不变，层间转移只更改槽位归属和映射，
不重新分配 GPU 权重空间，不重新捕获 CUDA Graph。默认每层至少保留 8 槽，
每 128 个 decode 步最多转移 16 槽；换入还受目标层现有的数量、耗时预算约束。
只在 Graph 回放之间完成必要等待、写入权重并发布映射。

容量策略使用各层 decode 专家调用频率、CPU 未命中计算成本和预计剩余生成步数，
仅在预计收益超过换入代价时转移。保留现有层内热点替换，prefill 不直接驱动层间容量调整。
跨请求的 decode 历史也可用于下一请求开始时的容量决策。
持久化保存名单和热度，不保存物理槽位；重启时重新规划总容量，再按历史继续学习。
这与主存 Marlin LRU 是否启用无关。

可选策略对象沿用 GLM 的字段，例如
`"adaptive_cache": {"interval": 128, "max_swaps": 16, "min_experts": 8}`。
容量调整也有统计、搬运和映射开销，是否更快需要以实际请求对照验证。

策略对象还支持独立控制两个容量决策阶段：`history` 和 `online` 均默认为
`true`。`{"online": false}` 只在请求开始时使用历史分配容量；
`{"history": false}` 只使用本次 decode 反馈调整容量。
这两个字段不关闭原有的层内专家替换或历史持久化。
`decay` 平滑的是本次请求各采样窗口的热度，不是跨请求历史的占比。
高级调优可设置 `horizon` 和 `safety_factor`，仅覆盖容量决策的收益窗口与
安全系数，不改变层内换入策略；未指定时沿用层内策略的值，在线窗口仍受
实际剩余输出步数约束。

每个共享池累计统计 `history_swaps`、`decode_swaps`，以及读取反馈、规划、
转移所花的时间。诊断用 benchmark worker 的 `dsv41_capacity_stats` 可读取这些统计。
`history_decisions` / `decode_decisions` 区分无法回本、
预算不足、层内替换优先及容量下限等原因。CPU 原生累计耗时用于成本估计，
不代表 CPU/GPU 并行后的关键路径等待；不能把命中率增量直接换算成加速比例。

本地三卡对照（3×CMP 170HX、PP `[7,7,26]`、关闭 DSpark、CPU 24/24、
512K KV 预算、2K prefill 分块）：单请求 32K 输入、1024 输出，各三次；
每次恢复相同缓存和学习初态，保留 kernel/Graph 预热。两组总槽数均为 1360。

| 请求 | 固定容量 prefill / decode（token/s） | 自适应容量 prefill / decode（token/s） | decode 命中率：固定 → 自适应 |
| --- | --- | --- | --- |
| 中文 | 6848.65 / 26.21 | 6795.01 / 26.38 | 62.79% → 60.26% |
| 英文 | 6937.41 / 28.36 | 6960.01 / 28.09 | 68.13% → 67.84% |

这组负载仅发生 15 个槽位的跨层调整，由请求开始时的历史触发；
decode 中没有额外通过收益门槛的容量转移。维护耗时每请求约 0.27–0.28 秒。
本次没有稳定速度收益，默认保持关闭。生成内容和路由会受已有 CPU/GPU
数值舍入影响，此对照不代表相同路由轨迹上的因果比较，也不外推到其他负载。
两组均通过八并发完整输出检查，GSM8K 小样本均为 11/16，不认证质量等价。

后续维护优化沿用上述机器、请求和缓存初态，比较原动态容量维护器与
CPU 提前筛选版本，中英文各三次：

| 请求 | 原维护器 prefill / decode（token/s） | CPU 筛选后 prefill / decode（token/s） | 每请求容量维护耗时 |
| --- | --- | --- | --- |
| 中文 | 6783.19 / 25.78 | 6785.95 / 26.27 | 0.289 → 0.196 秒 |
| 英文 | 7009.14 / 27.89 | 6979.09 / 28.97 | 0.285 → 0.178 秒 |

保留的改动先用向量化收益门槛过滤候选，再排序规划；同时快速构造换入成本数组。
原收益门槛、每卡预算和层内优先策略保持不变。两组都只发生 15 次历史容量转移，
在线转移为 0。英文单轮 decode 在 27.56–31.00 token/s 间波动，且生成路由不同；
均值增加 1.91% / 3.89% 不足以证明稳定的同比加速，默认仍关闭自适应容量。

同一份路由的事后静态最优比较中，自由分配容量的命中率增量只有中文 0.25、
英文 0.67 个百分点；这不是在线动态策略的绝对上限。短窗口分析也忽略了搬运代价。
实测继续寻找跨层候选并放宽门槛后，在线转移可达每请求约 1100 次，维护耗时
增至 4.8–5.0 秒，未获稳定速度收益。该策略和没有整机收益的 GPU 合并反馈读取
均已撤回；可通过阶段开关和拒绝原因统计继续评估其他负载。

## Decode 后处理重叠（方案 A）

`deepseek_v41_hybrid` 默认启用方案 A，不需要 benchmark worker、额外调度器或
重建 native 库。在此对象中设置 `"overlap_decode": false` 可恢复原同步路径；
删除字段会恢复默认开启。预填充和仅编码阶段沿用原处理方式。

方案 A 保留 GPU 状态更新的提交顺序，将 decode 的主机检查推迟到 draft 提交后。
主机等待对应输出的完成事件，复用已回传的采样计数；CPU 回调错误在输出交付前抛出。
每步完成函数保存请求和步数，缓存替换及线程切换仍保留原来必要的等待。

3×170HX、PP `[7,8,25]`、24 CPU 线程、原自适应 DSpark 的实验版本结果：

- 冻结缓存、32K 输入/1024 输出、三类单请求各五对：综合 +6.40%，95% CI `[+0.88%, +12.22%]`。
- 在线学习、统一 GPU/学习历史/空 host LRU 初态、各十对：综合 +4.86%，95% CI `[+1.66%, +8.16%]`。
  在线收益未达到预定 5% 默认采用门槛；并发吞吐也没有通过该门槛。
- 自然 GSM8K 256题：基线227题正确，A为231题；准确率差值区间 `[-1.17, +4.30]`
  个百分点，不能认证质量等价。调度时序影响验证形状，既有浮点归约差异可能改变输出。

上述结果来自迁移前的实验实现，不等于任意设备、上下文或流量的性能承诺。
本分支默认开启；更换设备或负载时应重新检查性能和模型质量。

正式实现与实验 A 的迁移回归使用固定 K=3、稳定 MoE 排序及在线学习：
256/256 行 logits、批次形状和输入完全一致，20 层缓存名单及学习状态一致。
16 道自然生成双方均为12/16正确，16/16条完整 token 序列一致；此小样本只用于
迁移检查。并发8请求取消后继续生成384个 token、请求排空及在线缓存更新检查通过。

## R8 专家换入

R8 专家换入默认开启，主存 Marlin LRU 默认关闭，启动命令可省略这两个字段。
CPU 继续读取原生 MXFP4_R8 bank，按需将三个投影复制到 pinned 缓冲，GPU 直接
生成既有 Marlin 权重和 scale 排列。只改变布局，不重新量化。需要主存缓存时，
可显式设置 `host_cache_gib`；设为 `12` 恢复此前使用的缓存预算。
旧版原生库缺少 R8 staging 接口时记录提示并使用原换入路径。

每个使用缓存的 GPU 共享两个 host staging 和两个 GPU raw 缓冲，不按层复制。
5120×2304 尺寸每张 GPU 额外使用约 35.9 MiB 显存和等量 pinned 主存；
自动规划先扣除 GPU 缓冲，再分配专家槽位。CPU memcpy 最多使用四个线程，
并受专家后端当前线程数限制。复制完成事件保护 host 缓冲，转换完成事件保护
GPU raw 缓冲；返回的 Marlin tensors 独立于循环缓冲。

启用后保留原有收益阈值和剩余输出长度约束，将 decode 最低检查间隔从 64
改为 16 个 verification step，单层最多换入两个专家、估计换入预算为 16 ms。
现有调度每步只访问一个层；实际间隔仍受层数和访问顺序影响。
替换仍发生在完成事件之后、下一次 Graph replay 之前，槽位地址保持固定。
设为 `false` 同时恢复原换入路径与原检查间隔/预算。

本轮 3×CMP 170HX、PP `[7,8,25]`、CPU `[24,24]`、512K KV pool、
自适应 DSpark 的在线测试，主存缓存预算12 GiB，32K 输入/1024 输出、
三类任务各五轮交替对照：
decode 综合 +10.01%，按轮配对 95% 区间 `[+6.96%, +13.15%]`。
每对恢复相同专家名单、学习历史和空 host LRU。4/8 并发各一组的整批输出吞吐
分别 +10.77%/+8.39%，包含 prefill 和排队。充分预热的128K中文单对中，
prefill 基本持平，decode +19.17%；这些单组数据不等于五轮统计结论。

自然 GSM8K 32题为基线30/32、候选29/32，代码解释8题双方8/8。
CPU原生结果、Marlin权重/scale字节及小规模GPU计算已核对一致；缓存选择改变
既有CPU/GPU舍入和生成路径，不能据此认证模型质量等价。本分支默认启用 R8
换入，并关闭主存 Marlin LRU。

同样的三张 CMP 配置、32K 输入/1024 输出，主存缓存12 GiB与关闭各做两轮
交替对照：中文decode为36.82→38.14 token/s，英文为38.01→39.66 token/s；
三worker合计主存PSS减少约11.21 GiB。连续英文请求第二次为39.96→42.65 token/s，
这里只有一对。主存缓存未命中会增加GPU→host回写；这些快速结果支持当前默认，
不代表其他设备或负载的最优容量。

四卡 PP `[3,4,3,30]`、CPU `[16,8]`、1M KV、5360个相同槽位的对照中，
32K三类任务各两轮：prefill提高约6.8%–11.8%；decode中文提高29.8%，英文提高2.0%，
代码主对照下降8.1%，补测存在较大波动。128K各一对的decode提高约4.5%–5.6%。
较早更新在高命中负载中尚未显示稳定收益，不能将三卡结果直接外推为四卡普遍加速。

## 自动 MPS 的退出清理

跨进程 GPU 专家会创建私有 CUDA MPS 实例。MPS 是独立后台服务，
需要通过控制命令关闭；参见 [NVIDIA MPS 管理说明](https://docs.nvidia.com/deploy/mps/appendix-tools-and-interface-reference.html)。
现有父进程管理器持有私有 MPS 实例，EngineCore 和 worker 退出后，
向此实例发送 `quit -t 10`。直接使用执行器时，由执行器自身负责关闭。
EngineCore 在资源清理期间忽略后续 SIGINT/SIGTERM，防止 Ctrl+C 后 API 补发的
终止信号打断清理；进程管理器仍用 SIGKILL 执行最终超时限制。
EngineCore 超过 60 秒清理宽限期被强杀，或提前异常退出，父进程仍会清理 MPS。
MPS 关闭命令单独最多等待 50 秒；命令失败、超时或仍有存活进程时，
父进程按私有目录和进程身份定向强杀，再等待退出。只有确认进程已退出才删除目录；
无法结束的进程会明确报错并保留目录。60 秒不是整个服务退出的总时限。
此修复不增加守护进程。如果连同负责清理的父进程一起 SIGKILL，仍会跳过清理。

显式设置 `CUDA_MPS_PIPE_DIRECTORY` 时，使用外部 MPS，vLLM 不启动或关闭该实例。
旧版本已残留的实例不会被新服务自动接管，需确认没有客户端后，通过其私有控制目录关闭。

## Strata 来源

### 可选的解码专家尾部跳过

`deepseek_v41_hybrid.route_tail_skip` 默认 `0`（关闭）。设为 `5` 或 `4` 时，
对完整解码 Graph，在一层的一次解码批次内按每个 token 的路由权重降序排名；
未命中 GPU 缓存的专家仅在其所有出现位置均排在保留范围之外时不计算。
当前 DSV4.1F 路由 Top-6：`5` 保留前五名，`4` 保留前四名。参数须小于模型
实际 Top-k。任意一次进入保留范围
便保护该专家在整个批次的所有路由，GPU 命中始终计算。相同权重按原路由位置排序。

被跳过的专家贡献为零，其余权重不重新归一化，属于有损近似，生成内容和 DSpark
接受率可能改变。该开关默认关闭，只作用于 `FULL_DECODE_ONLY` 的完整解码 Graph，
不处理 prefill 或混合批次的回退计算。支持多请求的整批保守裁剪：任意请求中的
前列路由都会保护本批次该专家的全部路由。并发增大时可能减少跳过比例；相同请求
的裁剪结果也受同批请求影响，即使 seed 相同也不保证生成内容相同。
回调容量沿用现有的最多 128 token 限制；八请求、七个 draft token 的上限为 64。
需要重新构建 `libdsv41_cuda` 并重启服务。

周期日志在 `Hybrid expert cache` 中打印 `Tail-skipped expert computations` 和
`Tail-skipped routes`。前者每层、每批次按专家去重后累计，后者统计省略的
token–专家贡献数，包括投机验证工作，排除预热和 padding。跳过比例的分母是启用
裁剪的解码回调中原始 CPU 未命中路由数。GPU 命中率的分母包含 GPU 实算、CPU
实算和跳过路由，避免将跳过伪装成缓存命中。统计复用已有推理完成后的采集链路，
不额外同步 GPU。

三张 CMP 170HX、RAM Engram、原自适应 DSpark、同一 16.249 GiB 专家缓存预算，
32K 输入 / 1024 输出、中英文与 Python 各三轮的整模配对复测：保留前五名 decode
综合提高 14.97%，完整请求输出吞吐提高 12.20%；保留前四名分别提高 23.60% 和
18.48%。GSM8K 5-shot 前 32 题为关闭 28/32、保留前五 29/32、保留前四 27/32，
均未触及输出上限；小样本不证明质量等价。该有损选项默认关闭，仅验证了单请求
RAM 场景。配置、原始结果与边界见
