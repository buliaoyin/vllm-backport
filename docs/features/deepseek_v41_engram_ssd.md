# DeepSeek-V4.1 Engram SSD 存储

CPU/GPU 混合模式可将完整 Engram 表保留在 SSD 上，按需读取，减少主存占用。
默认仍为 RAM 模式；在现有 `--additional-config` 中增加一个选项即可：

```json
{
  "deepseek_v41_hybrid": {
    "pipeline_layers": [7, 8, 25],
    "cpu_threads": [24, 24],
    "engram_storage": "ssd"
  }
}
```

其他启动参数保持不变。此功能需要重建 `libdsv41_cuda` 并重启服务，
见[混合推理构建说明](../contributing/deepseek_v41_build.md)。标准源码安装和
wheel 构建已包含 SSD 后端，无需单独的加载脚本或配置文件。

## 存储与资源

- 直接读取原始 safetensors，包括 Hugging Face 缓存的符号链接；不创建整表副本，
  不改变 FP8 权重、UE8M0 缩放或 n-gram 查表语义。推理期间需保留原权重文件。
- 当前后端为 Linux `O_DIRECT` + AIO，经固定主机缓冲区传入 GPU，启动日志会明确显示。
  这不是 GDS；不依赖 cuFile 或 nvidia-fs，也不会静默改用能填满主存的普通文件缓存。
- 默认热点行缓存**总计 1 GiB**，两张表各 512 MiB，保存原始量化字节。
  可选 `engram_cache_gib` 设置整个模型的预算，设为 `0` 可关闭。
  不再设固定的 8 GiB 上限；超过模型实际 Engram 表大小时自动截到表大小，
  按原始 FP8 数据与缩放计算，此模型合计约 188.83 GiB。每张表也分别封顶，
  较小表用不完的预算分给其他表。索引元数据计入缓存预算。
  内存预检查使用封顶后的预算，保留可用主存及 cgroup 保护；缓存不随请求无限增长。
- 每张表另有 4 MiB 直接 I/O 缓冲区，以及由 `max_num_batched_tokens` 限制的行号、
  读盘规划和传输缓冲区。默认 2,048-token 工作区下，每张表约需 18 MiB 主机工作区，
  新增 12.4 MiB GPU 工作区；原有 BF16 查表结果缓冲继续复用。
- SSD GPU 工作区在模型初始化时分配，随后预留 KV、采样完整上下文工作区，
  最后自动计算专家缓存容量。主机预检查同时计入有限的 Engram 行缓存预算。

读取按 4 KiB 页去重，相邻页合并至最多 128 KiB，每张表最多 128 项未完成 I/O。
没有额外的常驻读盘线程池。各 PP 阶段在本地层计算前提交读取，消费行数据时等待事件。
完整 CUDA Graph 可以包含读盘回调；分段图分别记录提交和消费动作，避免跨图段的缓冲区失效。

SSD 缓存只保存不可变的查表结果；请求历史、图像无效位置及 DSpark 草稿回退沿用模型的
原有状态管理。磁盘读取失败或文件截断会报错并终止推理，不会用零向量代替真实权重。

## 适用范围

当前支持 Linux、CUDA、TP1 的 DeepSeek-V4.1 CPU 混合模式，使用 mmap safetensors 加载。
显式的 eager/prefetch 加载模式会被拒绝，以免启动时重新把整表读入 RAM。
模型文件所在文件系统须支持直接 I/O；不支持运行中替换 Engram 权重。

SSD 会增加实际磁盘读取。冷请求和大量新 n-gram 的 prefill 代价取决于随机读取能力，
热点缓存可减少重复访问，但不能保证任意新输入都达到 RAM 模式吞吐。

## 实测参考

2026-09-18，三张 CMP 170HX、EPYC 7532 / NPS auto、EXT4 NVMe，
PP `[7,8,25]`、CPU `[24,24]`、1M KV 预算；固定相同的 528 个 GPU 专家槽、
专家名单及学习状态。每个请求为 32K 输入、256 个实际输出。三种题目先分别清空
缓存测冷请求，再交替三轮合并计速；首轮仍含输入切换后的缓存填充。
Prefill 以完整 TTFT 计算，包含 128-token decoder 尾回放。以下三点为初版 128 MiB
缓存的结果。

- 开启 DSpark 3 草稿时，worker 主存 PSS 从 **341.96 降至 153.25 GiB**。
  SSD 模式还在 256 GiB 进程组限额下完成了 512K 输入检查。
- 中文、英文和代码题：开启 DSpark 时，SSD prefill 比 RAM 低 **9.9%–12.5%**，
  decode 低 **0.2%–1.1%**。
- 不重复源码输入、关闭 DSpark：prefill 从 **5,690 降至 3,207 tok/s**，
  decode 从 **29.51 降至 29.07 tok/s**；冷请求 TTFT 从 **5.78 增至 11.22 秒**。
  这组输入的行缓存命中率约 48%，读取等待集中在较早消费的第 1 层。

这些数据说明内存节省有效，decode 基本保持，但不能据此承诺新内容的 prefill 不降速。
它们也不代表四卡、其他 SSD 或其他 NUMA 配置的性能。

### 扩大热点行缓存

同日、同三卡配置补测了 256 MiB、512 MiB、1 GiB 总预算。下表为关闭 DSpark、
不重复源码构造的 32K 输入、256 输出，重复该输入预热后三轮合并的结果：

| 行缓存总预算 | Prefill（tok/s） | Decode（tok/s） | 行命中率 | 读取量（GiB/请求） |
| --- | ---: | ---: | ---: | ---: |
| 128 MiB | 3,207 | 29.07 | 47.89% | 4.887 |
| 256 MiB | 4,433 | 29.51 | 79.00% | 2.001 |
| 512 MiB | 5,685 | 29.73 | 96.13% | 0.371 |
| 1 GiB | 5,782 | 29.67 | 99.59% | 0.040 |
| RAM 整表 | 5,690 | 29.51 | — | 0 |

这组工作集下，512 MiB 已取得大部分吞吐收益；1 GiB 相比 512 MiB 的 prefill
再提升约 1.7%，主要优势是继续减少读盘。当前默认已采用 1 GiB，
启用 SSD 模式后无需显式设置 `engram_cache_gib`。
1 GiB 档启动后 worker PSS 合计为 153.84 GiB，128 MiB 档为 153.01 GiB。

以上是可复用输入的结果。各 SSD 容量清空行缓存后的该源码请求 TTFT 仍约
11.2–11.4 秒，RAM 为 5.78 秒；增加容量没有消除首次读取新内容的 SSD 延迟。
这些冷请求只测一次，新增容量的首个请求还包含少量形状 JIT，不将细小差异归因于容量。

1 GiB 还补测了 DSpark 3 草稿下的中文、英文、代码交替请求：相对 128 MiB，
prefill 提升约 5.2%–14.9%，decode 变化为 −0.8% 至 +1.2%。单请求的输出文本、
逐层专家路由及 DSpark 接受计数均与 RAM 基线一致。
