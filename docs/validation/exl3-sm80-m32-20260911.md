# EXL3 SM80 M=32 专家 prefill 优化（2026-09-11）

本轮验证了“优先优化 SM80 专家 GEMM”的方向，并实现了跨行复用解码结果的
M=32 原型。它通过独立构建和 benchmark Worker 开关启用，生产默认路径保持现状。
整模型测试固定 PP `11/11/11/12`，GPU3 Blackwell 使用原生内核。

## 对优化建议的判断

总体合理，但需要区分源码事实、测量和推断：

- 旧报告中约 2.33–2.35 s 的专家区间来自 512-token chunk；平均约 28 行及
  78%–79% 有效行比例对应 1024-token chunk。它们支持相同方向，但不能混作
  一次测量进行定量归因。本轮最终整模型比较统一使用 1024-token chunk。

- 原生专家内核每 16 行重新执行 GEMM 的取数、trellis 解码、计算和归约。17–32 行
  使用一次 M=32，与两次 M=16 有相同的行 padding，因此 M=32 不只适用于极热点专家。
- 真实 1024-token 路由中，采用 M=32 加短尾 M=16 的有效计算方式，可以保留
  原有 77%–79% 行利用率，减少约 36%–38% 的权重解码遍历。它是循环次数估算，
  不是 HBM 流量测量；重复权重读取可能命中 L2。
- 原生实现已经使用 `cp.async` 多级缓冲，trellis 解码结果也直接形成 MMA 的 B
  fragment。借鉴 [Marlin](https://github.com/IST-DASLab/marlin) 应着重于实际流水线
  和寄存器布局，不能把异步加载或直接 fragment 解码当成当前完全缺失的能力。
- 更大的 M 需要布局改造和寄存器预算。把两套完整 M=16/M=32 GEMM 分支塞入同一个
  内核，虽然减少 padding，却明显增加寄存器溢出。
- 不能由已有外部专家区间直接推断内部同步占比。本轮 GEMM 区间仍包含内部 block
  同步、K 切分锁和归约；尚无硬件计数器证据把这些成本与取数/解码精确拆开。

## 内核分段证据

Nsight Compute 返回 `ERR_NVGPUCTRPERM`；没有修改驱动设置。改用独立编译的
`clock64()` 版本，每个 block 的 thread 0 将累积周期写入专用槽位。
这是 block 周期构成，不是 SM 利用率，也不能相加成请求延迟。

layer 3 / 1024 tokens 的三次采样约为：

| 区间 | block 周期占比 |
| --- | ---: |
| gate GEMM | 30.36% |
| up GEMM | 30.06% |
| down GEMM | 33.23% |
| gather、输入 Hadamard 及其 barrier | 1.95% |
| 中间 Hadamard、激活及其 barrier | 1.84% |
| 输出 Hadamard、scatter | 1.11% |
| gate/up 与 down 后的显式 group barrier | 0.65% |
| 专家调度及其 barrier | 0.42% |

计时版本约 24.93 ms，原生约 22.25 ms，插桩开销约 12%；插桩也增加了寄存器
溢出。因此 94% 仅作为方向证据，不作为未插桩内核的精确成本分解。
退役 block 留下的 SM 空闲也不计入这些槽位，因此不能据此排除 tile 级调度收益。
layer 22 的采样也呈现相似构成。现阶段应继续优先研究 GEMM 内部，workspace
变换及外层调度暂不应排在前面。

## 实现与消融

原型补丁位于 `benchmarks/kernels/exl3_m32/rows.patch`，基于 ExLlamaV3 1.4.8 / commit
`6ff3a17ea7f3d0026b273d43239398d57f71b788`，保留其 MIT 许可证。

- 一份解码后的 B fragment 被两组 M=16 A/C fragment 消费。
- A fragment、C 累加器、共享内存 K 归约及输出地址都扩展了 M 维。
- 对最多 16 行的短尾，跳过第二组 A fragment 加载、MMA 和 K 归约。
- 寄存器 fragment 流水线从三级改为两级，共享内存仍为三级。
- 保留 K=32、N=256、512 threads、8 blocks/expert group、90 KiB shared memory、
  原有专家调度、Hadamard、激活、scatter 和 FP32 MMA 累加。
- 启动器验证 SM80、4-bit mul1、维度整除、同设备连续张量及 grid 的全驻留条件。

尝试过 N=128/256、两级/三级 fragment staging、完整 M16/M32 分支、统一 M32
及短尾条件执行，并额外检验 K=16。N=128 或直接混合分支存在明显寄存器/调度开销。
K=16 未优于保留 K=32 的 M32；其归约顺序变化带来的输出差异也更大。
最终保留统一 M32 加短尾条件执行。

从切片几何看，当前 GLM 的 gate/up 为 K=4096、N=2048，down 为 K=2048、
N=4096；N tile=256、group width=8 时，每个 block 的切片都覆盖完整 K 列，
不会进入跨 block 的部分 C 读回路径。因此这里不能把全局 split-K 往返当作已经
证实的主瓶颈。原型保留了原有锁协议；block 内 K 归约与同步仍然存在。

最终内核 ptxas 报告 128 registers/thread、8-byte stack frame、4-byte spill stores、
2-byte spill loads；初版完整混合分支最高出现数百字节的 spill stores/loads。
这些数字是静态编译报告，不是动态显存访问总量。

## 真实路由微基准

使用 GLM-5.3-Flash EXL3 完整 288 专家权重和捕获的真实路由。计时包含完整专家
wrapper 的 GPU 工作，不含 Python replay 开销；每个样本一次 CUDA graph replay，
15 次采样取中位数。每次计时前写入 256 MiB 驱逐缓冲区，其时间不计入结果。

初轮闭包调用使 FlashInfer 的 cold-L2 请求被禁用，相关 JSON 已明确标注为热缓存。
下表采用随后显式清理 L2 的复测。2048-token 输入拆成两个 1024-token chunk。

| 层 / GPU | 输入 token | 原生 ms | 仅两级流水线 ms | M32 ms | M32 短尾条件执行 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 3 / CMP 170HX GPU0 | 512 | 13.97 | 12.85 | 11.17 | 10.74 |
| 3 / CMP 170HX GPU0 | 1024 | 22.26 | 20.48 | 15.97 | 15.61 |
| 3 / CMP 170HX GPU0 | 2048 | 44.19 | 40.65 | 31.14 | 30.15 |
| 22 / CMP 170HX GPU1 | 1024 | 21.35 | 19.86 | 15.21 | 14.75 |
| 22 / CMP 170HX GPU1 | 2048 | 42.98 | 39.53 | 30.67 | 29.74 |

原生后置对照相近；1024-token 测量有约 1% 的前后波动。优化版相对原生的最大
观测 relative L2 在这些真实路由配置中约为 2.5e-6。该一致性检查之外，单元测试
还使用独立的显式旋转/重建矩阵参考。

## 精度与整模型验证

`tests/quantization/test_exl3.py` 在 SM80 上 49 项通过，新增 12 个可选原型用例
覆盖 9/16/17/31/32/33/63/64/65/129/513/1025 行、热点专家、容量边界和 graph
重放时改变输入/路由。未构建原型时，这些额外用例跳过。

整模型为 GLM-5.3-Flash，TP=1 / PP=4，实际 decoder 层分配已检查为
`0–10 / 11–21 / 22–32 / 33–44`。仅前三张 SM80 卡的 8/11/11 个量化专家层
启用 M32，最后一张 Blackwell 保留原生路径。B1、chunk=1024、KV=8 GiB、
max_model_len=66560、输出 32 tokens，各长度预热一次、测量三次，无 prefix cache 命中。

同一模型进程依次执行原生前测、M32、原生后测；检索答案 **36/36** 正确。
下表 TTFT 单位为秒，吞吐为 `prompt_tokens / prefill_interval` 的样本中位数。
收益保守地使用原生前测计算。

| 输入 | 原生前测 TTFT | M32 TTFT | 原生后测 TTFT | TTFT 降低 | 原生 prefill tok/s | M32 prefill tok/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 8K | 3.4171 | 2.7844 | 3.4935 | 18.5% | 2399.4 | 2944.9 |
| 16K | 6.1751 | 4.9847 | 6.2848 | 19.3% | 2655.0 | 3289.7 |
| 32K | 11.8094 | 9.4219 | 11.9005 | 20.2% | 2776.3 | 3480.4 |
| 64K | 23.2131 | 18.3853 | 23.2351 | 20.8% | 2824.7 | 3566.9 |

原生前后 TTFT 漂移为 8K +2.24%、16K +1.78%、32K +0.77%、64K +0.09%，
不足以解释约 18%–21% 的收益。吞吐提高约 23%–26%。这组 B1 固定长度
测量的 decode 约 38.6–39.4 tok/s，原生与 M32 差异小于 1%；本轮主要收益在 prefill。

与之前 NVFP4/AWQ 的最终比较沿用[固定分层报告](exl3-fixed-pp-comparison-20260910.md)
中同样 PP、chunk、KV、输入 token IDs、预热/重复和输出长度的结果。汇总脚本逐项
检查这些配置和实际层编号相同；**本轮未重跑 NVFP4/AWQ**。

| 输入 | EXL3 M32 TTFT / tok/s | NVFP4 Marlin TTFT / tok/s | AWQ Marlin TTFT / tok/s |
| --- | ---: | ---: | ---: |
| 8K | 2.7844 / 2944.9 | 1.7541 / 4676.9 | 1.6830 / 4877.2 |
| 16K | 4.9847 / 3289.7 | 3.1921 / 5139.4 | 3.0599 / 5362.2 |
| 32K | 9.4219 / 3480.4 | 6.1370 / 5345.3 | 5.8938 / 5567.4 |
| 64K | 18.3853 / 3566.9 | 12.1481 / 5400.3 | 11.7093 / 5602.6 |

64K 时 EXL3 M32 的 TTFT 仍为 NVFP4 的 **1.51 倍**、AWQ 的 **1.57 倍**。
没有追平 Marlin。两种 Marlin 路径均为 W4A16；不同量化格式、权重及专家路由不完全
相同，AWQ 的最后一个专家层不量化。因此该表是对应模型产物的服务性能比较。

没有把此前 `10/7/7/21` 分层的收益并入本轮内核收益。

64 题 GSM8K 子集、B4、最多 768 输出 tokens、temperature=0：原生和 M32
均为 **62/64**，64 个最终数值答案逐题一致；错误均为 id=9（500，正确 460）和
id=12（12，正确 13）。只有 **18/64** 个完整 token 序列相同，不能宣称逐 token
等价。这个小样本未观察到最终答案准确率下降，也不能证明普遍精度无损。

同一模型进程另采样一次 8K 请求的专家区间，均为 chunk=1024：

| GPU / PP rank | 原生专家 ms | M32 专家 ms | 区间耗时降低 |
| --- | ---: | ---: | ---: |
| 0 | 1380.27 | 940.86 | 31.8% |
| 1 | 1907.56 | 1323.45 | 30.6% |
| 2 | 1900.68 | 1340.76 | 29.5% |
| 3 | 742.59 | 747.19 | -0.6% |

GPU3 继续运行原生代码，其小幅变化属于采样波动。GPU1/2 的约 30% 专家区间
降幅与微基准一致。这些区间包含 wrapper launch gap，且各 rank 可能重叠；
不能相加作为请求 TTFT。上面的干净性能测量先于这次插桩与模型输出评估完成。

## 当前交付范围与下一步

可复现构建、内核补丁、真实路由微基准、模型 Worker 开关及精度测试均已放入仓库。
使用方法见 [原型 README](../../benchmarks/kernels/exl3_m32/README.md)。

当前通过 benchmark 选项启用，不改生产默认行为。其私有 ExLlamaV3 ABI、SM80、
4-bit mul1 和维度约束仍然存在，尚未覆盖其他模型形状、M64、其他 GPU、混合位宽、
持续多请求服务或排队/TTFT 权衡。因此可以确认本配置的性能收益，不能把它描述为
已经完成通用生产后端或已追平 Marlin。

进一步优化应优先围绕这版 GEMM 的实际流水线和热点专家更大 M 的寄存器预算。
tile 级调度仍需结合 SM 空闲/内部等待证据；外层 workspace 与跨请求聚合不是本次
约 20% 整模型收益的来源。本轮没有重试此前失败的 FP16 热缓存等方案。
