## 单卡微基准

CMP 170HX，256 个专家、每 token 路由 6 个专家、block size 8、int32 路由 ID，固定随机种子。先核对两条路径的有效 token→expert 分组与总 padding 数一致；组内顺序允许不同。

CUPTI Python 在当前环境不可用，使用 CUDA Graph + CUDA events，每次在计时区间外清理 64 MiB L2，60 次样本并交替执行顺序；计时不包含主机分配、编译和输入生成。测量对象是分组操作，使用延迟衡量，不给它套用 GEMM 的 TFLOPS 指标。

| token 数 | 原生 CUDA，μs | 确定性路径，μs |
| --- | ---: | ---: |
| 1 | 12.29 | 103.42 |
| 8 | 12.29 | 103.42 |
| 16 | 12.29 | 102.40 |
| 32 | 12.29 | 147.46 |
| 64 | 13.31 | 153.60 |

单请求、7 个草稿 token 的验证批次通常为 8 个 token。几十个模型层中重复的分组开销可以累计至毫秒级。冷 L2 微基准不等于整模型运行时的每层耗时，不能将微基准差值直接相加当作整模型加速实测。

## 后续处理建议

最直接的诊断方式是在当前仓库原启动命令前加 `VLLM_DETERMINISTIC_MOE_ALIGN=0`；其他参数不变。也可在同一 shell 先执行：

```bash
export VLLM_DETERMINISTIC_MOE_ALIGN=0
```

该设置让当前 MoE 分组选择与参考仓库一致，需要重启服务才会进入新捕获的图。它会恢复原生分组的非确定性组内顺序，可能改变浮点累加和输出文本；不是仅改变计时行为的无语义开关。即便开启它，也不能保证所有其他算子都具有确定性。

长期优化应优先将确定性分组中的多个小操作融合，尤其针对 DSpark 常见的 8-token 小批次，在保持稳定路由顺序的前提下降低成本。若按模型设置性能默认值，应先验证 DSv4，并保持 GLM/Qwen 的既有行为；不要直接全局关闭来掩盖成本。

`DSV4_LOGITS_ROW_CHUNK` 作用于 prefill logits，本次双方都设为 64。双方 DSpark 默认均为 greedy、局部 argmax 默认关闭，当前自适应验证默认也是关闭；不能把新功能“存在”当成默认运行额外草稿算法的证据。TP 分工和 all-reduce 开关也不是此次 TP1 的首要解释。
